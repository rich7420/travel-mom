## 優先修正的具體問題

P1 表示會阻礙日常工作，或正式使用前必須處理；P2 表示可信度與完整性問題。標註「實測」的項目已操作或重現；「程式檢查」表示從實作確認，沒有宣稱做過相應實機測試。

### P1 案件修改會先寫入不合法資料

**實測。** `PATCH /api/cases/{id}` 接受任意字典，[`CaseRepo.patch`](../app/repositories.py) 更新並提交後才重新讀取模型。用合成案件送入 `adults=-1` 與 `status=bogus`，得到 HTTP 500；資料庫已保存這兩個值，接著列出案件也得到 HTTP 500。

影響：一次錯誤修改可能讓所有案件列表、首頁與提醒讀取失敗。修改方向：建立 typed patch 模型，合併現有值後驗證人數、日期與狀態，再在同一交易內寫入；不合法請求回傳 422，原資料必須不變。另做資料完整性檢查與修復工具。

### P1 接完一位客人後無法自然接下一位

**實測。** [`startGuided(false)`](../app/mom_static/app.js) 沿用同一個瀏覽器引導 ID，[`GuidedIntake.start`](../app/services/guided.py) 會接回已完成的 session。再按「新客人」仍顯示前一位的完成畫面，必須手動「重新開始」。完成畫面「找機票」按鈕又被當成引導回答送回後端，沒有打開查價表單。

修改方向：未完成才續接，已完成就建立新 session；完成後以案件 ID 導到真正的工作。驗收：連續建立三位客人、刷新與接續未完成案件，均不混淆；完成後各捷徑實際開啟對應流程。

### P1 已知需求沒有帶入查價且遺漏親子資料

**機票帶入已實測；飯店欄位為程式檢查。** 用「東京、指定日期、2大1小」建立案件，從案件進入機票表單，目的地與日期仍空白，小孩預設 0。飯店送出的 `children_ages` 固定空陣列；機票 `infants` 固定 0。

影響：重複輸入增加錯誤，查到的票價／房價可能沒有包含實際旅客。修改方向：從案件帶入日期與旅客組成，讓城市對應機場由使用者確認；補小孩年齡、嬰兒與分房需求。不得把空白年齡解讀成沒有小孩。驗收：2大1小進入查價後人數保留，親子飯店缺年齡時要求補一題。

### P1 媽媽模式無法從查完走到選案與報價

**程式檢查及離線畫面實測。** [`openSearchProgress`](../app/mom_static/app.js) 只畫進度；「看機票方案」也進入同一個進度畫面，沒有結果比較、選取、重新確認與 preflight。首頁又排除 `completed` 的查詢；沒有選方案時，工作可能停在「看方案」，但實際不能選。

修改方向：完成結果仍留在案件內，提供候選方案卡、選取、重新查價與變動提示，再建立報價草稿。`completed` 與「有可用價格」應分開呈現；無結果、人工接手、失敗、等待開始需各有下一步。驗收：合成流程可在媽媽模式完整選案，不進管理工作台；沒有結果時不顯示可報價。

### P1 後端工作記錄有保存但沒有可靠續跑

**程式檢查，未做崩潰測試。** [`app/main.py`](../app/main.py) 用進程內 `BackgroundTasks` 執行，啟動時只初始化資料庫，沒有復原工作。停止服務可能留下 `running`；開始端點會拒絕再次啟動這個狀態。啟動的讀取／寫入也未形成原子 claim。

修改方向：先加入工作 lease、心跳、停滯偵測、原子 claim 與人工重試，再拆可靠 worker。重試只限可重入的查詢；登入、驗證與購買不能自動重播。驗收：查詢中重啟服務後恢復到明確可接續狀態，連點開始不產生兩份工作。

FastAPI 的背景工作機制是在回應後執行；本專案需要的跨進程復原是額外工程需求，不能只靠現有背景函式。參考 [FastAPI 官方文件](https://fastapi.tiangolo.com/tutorial/background-tasks/)。

### P1 正式客人資料與報價證據的處理不足

**程式檢查。** 一般案件與 audit payload 是明文；Fernet 只保護另存的 vault。草稿服務把基本案件及客人貼入的訊息交給 Gateway，沒有統一遮蔽與最小化，也沒帶入已選方案及查詢證據。回饋遮蔽是特定格式規則，不保證遮掉所有姓名、地址、生日與證件。

修改方向：區分業務資料與敏感旅客資料，限制模型可見欄位，記錄存取與保存期限；回覆使用已核對的結果與來源時間，不從自由文字推測價格。正式客人試用前完成登入身分、備份還原與敏感資料流程。驗收：護照、完整生日、付款資訊不進一般提示／回饋；來源不足時草稿只說待確認。

### P2 工作按鈕與連線標示會造成錯誤期待

**行程入口與降級草稿已實測，其餘為程式檢查。** 「做行程／查簽證」僅跳提示；「準備行前資料」回到案件。AI 停用回傳設定訊息，但畫面仍提供「複製草稿／可以直接用」。`AI 已連線` 只讀啟用設定，並未探測 Gateway。

修改方向：未完成的工作標明可用狀態或提供真正的人工替代入口；降級結果不當成客戶草稿；區分已設定、已探測、查詢成功，顯示原因與可做的下一步。

### P2 今日清單與聊天入口尚未一致

**程式檢查。** [`build_mom_home`](../app/services/mom_ux.py) 在最近 20 筆案件內排序，舊急件可能漏掉；沒有到期任務。LINE router 仍說飯店流程未開發，航空清單也不完整。Webhook 把助理生成與送出都留在同一請求內。

修改方向：先從全部未結案工作與具體到期時間選急件；Web／LINE 共用同一套案件動作。對聊天入口使用驗證後入列、保存回應與送達狀態。LINE 官方也建議非同步處理 webhook 事件，避免後續請求等待，見 [LINE 官方文件](https://developers.line.biz/en/docs/messaging-api/receiving-messages/)。

## 建議的產品修改方向

媽媽最需要的可能是「不用到處找資料、知道今天要催誰、給客人的內容不漏項」。這是依上述工作假設提出的產品判斷，不是已量測的使用者結論。工具應在每個案件內保留需求、方案、報價、訊息與待辦，並讓她隨時知道：現在等誰、下一步做什麼、何時到期。

以下是建議的目標流程；報價、期限追蹤與訂購後工作需要新增業務模型與介面。

```mermaid
flowchart LR
    A[接收詢問] --> B[確認需求與旅客]
    B --> C[官網或人工供應商查價]
    C --> D[候選方案與來源]
    D --> E[版本化報價]
    E --> F[客人同意與到期追蹤]
    F --> G[重新查價與人工訂購]
    G --> H[正式確認單與收付款紀錄]
    H --> I[文件及行前交付]
    I --> J[旅途中協助與結案]
```

### 先接得住每天的詢問

加案件編輯、需求摘要與溝通時間軸。貼一段客人訊息後，先提取城市、日期、人數、預算與偏好，顯示「已有資訊／還缺什麼」，由媽媽確認再存；不確定的資料保留未知。重複客人與多次旅行需分成 `Customer` 與 `TripCase`。

接著補語音輸入、城市／機場選擇、親子與團體資訊。主畫面只呈現「接新詢問、回客人、查價、做報價、追進度」，每一步沿用案件脈絡，降低重新輸入。

### 能做旅行社真正的報價

新增報價版本，區分供應商成本、對客售價、服務費、折扣、幣別與總價；外幣需保存換算依據與時間。報價明列包含／不包含、票規／取消規則、有效期限、價格與庫存仍需確認。修改方案產生新版本，舊版本與客人採用哪一版可追溯。

輸出可預覽的繁中訊息與 PDF，價格由結構化項目加總，文字由模板或 AI 整理。提供「已人工確認」紀錄，不讓模型自由算總價或把查價當成保留機位。

保留官網查詢，另加**人工供應商報價入口**：媽媽可以錄入同業／票務／飯店窗口提供的價格、條件、來源與有效時間，明確標示來源類型，不假裝是官網資料。這可減少工具被單一自動瀏覽流程限制。若公司既有供應商接口可合法使用，再逐步接入；本次沒有假設具備任何 GDS 或供應商 API 權限。

### 知道今天要催誰與不能錯過哪些期限

新增明確待辦：回覆承諾時間、報價追蹤日、訂金／尾款日、開票時限、飯店免費取消期限、缺文件與行前交付日。每項有來源、到期時間、責任人、完成／延後原因及下一次提醒。

客人同意方案時，系統建立下一步清單，不自動宣布已訂妥。提醒區分「等客人、等供應商、等我們」；逾期先通知內部業務，不直接代她催客或取消訂單。手機首頁先處理真正到期的事，已完成案件不佔急件位置。

### 訂購後把資料收齊再交付

新增 `BookingRecord` 與確認單附件。先支援人工錄入或貼入確認內容，再做 Email／PDF 擷取；擷取結果與原檔並列，人工核對姓名、日期、PNR／確認號、金額、房型與付款狀態，才標記已確認。

從正式確認建立後續待辦：座位、行李、接送、旅遊保險需求、證件缺件與行前文件。收付款先記錄應收／已收／未收與憑證，不接觸信用卡支付。行前包整合已確認票券、住宿、集合與聯絡資訊；簽證／入境內容另走權威來源與查詢時間的查證流程，不能用通用生成文字當核准結論。

### 有異動時能快速找到相關客人

進一步建立航班／訂單與案件的關聯，收到供應商變更時列出受影響案件、原內容、變更內容與待處理事項，先草擬個別回覆並人工核對。旅途中提供聯絡清單與已確認資料；結案後留下偏好與服務紀錄，減少下次重問。

這些是後續能力，不應在未有正式訂單、來源與授權時直接開放自動監控、發訊或改退票。

## 分階段落地與驗收

以下順序代表依賴關係，不是已承諾的工期。工程量為相對估計，尚未做開發排程。

| 階段 | 交付內容 | 驗收與可量測目標 | 相對工程量 |
| --- | --- | --- | --- |
| A 把現有流程走通 | typed 案件修改、接第二位客人、完成捷徑、帶入需求、旅客組成、結果選取、真實狀態 | 5 個合成案件從接單走到選案，不需管理工作台；錯誤更新不改資料；小孩與嬰兒不漏；來源不足不能報價 | 中 |
| B 做出可用報價工作台 | `Quote`／`QuoteVersion`、人工供應商來源、成本與售價、草稿/PDF、客人決定 | 同一案件三版報價可追溯；總價與明細一致；供應商成本不出現在對客文件；每版有有效時間 | 中至大 |
| C 能追蹤期限與訂購確認 | `WorkItem`、`BookingRecord`、收付款紀錄、人工確認、行前清單 | 今日清單涵蓋全部未結案到期任務；確認單欄位逐一核對；待辦完成後停止提醒 | 大 |
| D 安全可靠的實際試用 | 工作 lease／復原、身份與角色、備份還原、敏感資料政策、優先官網實機驗證、內部 LINE | 重啟不中斷案件；重複事件不重建案件；還原演練成功；每個供應商公開實測成功／接手比例 | 大，可與前面並行 |
| E 延伸旅行全生命週期 | 文件擷取、行前包、異動處理、團體名冊、偏好與受控 Skills 改進 | 文件差異清楚提示；異動可對到案件；學習候選需回歸與人工審核，能回復前版 | 大 |

D 的身份、資料與備份門檻必須在真實客人資料導入前完成；不用等功能全部做好才處理。單人試用可先延用 SQLite 與現有服務層，避免同時重寫前後端。需求擴到多人共用、長時間查價或多瀏覽器 worker，再評估 PostgreSQL 與獨立工作服務。

建議新增資料物件先圍繞原 `TripCase`：`Customer`、`Traveler`、`QuoteVersion`、`WorkItem`、`BookingRecord`、`CommunicationRecord`、`Attachment`，以版本化 migration 逐步擴充。不要讓媽媽介面、LINE 與工程工作台各建一份資料庫。

試用先量測完整任務完成率、處理時間、重填次數、人工接手率、草稿修改率與漏期限數。目標值需先取得基線；例如可把「重填已知資料為零、遺漏旅客為零、不合法資料提交為零」設成階段 A 的硬性驗收。官網測試要分清「通過合約驗證」與「真的取得可用報價」，安全停下也不算自動查價成功。

## 建議先做的具體開發包

**下一個開發包是「案件需求帶入、查價結果選取與回覆草稿」；先解決上述 P1 的資料更新與引導問題，再使用現有比較／重新查價後端，把媽媽模式的流程接通。** 這個範圍可以直接用目前架構完成，驗收時從接新客人走到整理一份有來源的方案，付款與開票維持人工。

完成這包後，第二包優先做「版本化報價＋追蹤期限」，比先增加更多航空公司、讓 Skill 自動進化或換整套技術棧，更能支援每天的實際工作。這個優先順序是本次產品評估的建議，後續再以媽媽實際完成任務的時間與卡點調整。
