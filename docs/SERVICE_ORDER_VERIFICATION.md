# Manual service-order verification

Date: 2026-10-05. Scope: dedicated change, cancellation, refund and in-trip incident work orders in the existing Mom web interface, schema 806. Supplier operations, actual transfers, emergency calls and customer notifications remain human actions.

## Implemented behavior

- Request, original booking targets, owner/due/urgency/contact; virtual deadlines route to the order, including future open orders as the case's next action.
- Supplier reply, applicable contract/policy source and expiry, proposal, per-currency four-direction cash totals and whole-case final customer due. Informational fee breakdown is already included, never summed again.
- Revision-bound customer decision and execution evidence, immutable confirmed/refused supplier result, append-only communications/corrections and checked booking-result rebinding.
- Installment settlement uses the existing ledger, global refund caps and per-order remaining caps. Same UUID/actor/content replays exactly once. Voiding linked cash increments order revision and invalidates financial resolution.
- Resolution checks consent, execution, supplier result, exact cash and current booking/document/pack evidence. Previously delivered changed trips require a current replacement delivery. Immediate incident help needs no quote or payment approval; monetary incidents can use quote-free service accounting.
- Full cancellation supports retained fees and explicit cancellation closure; partial cancellation keeps remaining travel through an amended adopted quote. Each currency's latest resolved money assessment must match today's adopted quote. Historical settled orders remain settled after later changes or business withdrawal. Closed cases produce no service deadlines.
- Single sheet, one promoted next step, secondary actions in native disclosure, full consent summary, separate read/error/retry states and named-input preservation on conflict. Consequential retries lock on changed assessment/booking bindings. Uncertain writes freeze inputs, retain an immutable in-memory request, and reconcile a metadata-only receipt before retry or reload. Authentication expiry clears contact drafts/displays.
- Seventeen guide anchors remain stable; dedicated instructions are under the deadlines chapter. English architecture and workflow-coverage documents include the new flow. Applicable official sources were checked on 2026-10-05; no common legal percentage or eligibility engine was introduced.

1. **Actor change during an awaited receipt:** the form checks its actor only before the receipt GET. Switching to Admin while that GET is pending allows Mom's existing form to POST and commit under Admin. Checking the actor before the asynchronous wait is insufficient.
2. **Tagged intent becomes locally unrecoverable:** losing that committed response leaves metadata tagged as Mom. Mom's receipt 409 causes `recover` to set `unavailable_for=Mom`, although the comment describes actor-less legacy metadata. Admin also excludes the intent because it is tagged as Mom. Both accounts can read the list but neither can reconcile this intent through the UI.
3. **Fingerprint conflict discards a committed retry ID:** when an original request commits between receipt `committed=false` and a second submission using that same UUID with different content, the server correctly rejects the second body with 409. The browser then forgets the committed UUID; a subsequent submit mints another UUID and creates a second work order. Two tabs do not generally share sessionStorage: this applies to copied/cloned pending metadata or overlapping requests retaining the same UUID. The reproduction schedules another real HTTP write at that precise boundary and verifies two created records.

These findings were **unfixed** at that review-only checkpoint; the completion below corrects them. They qualify the earlier five-fix completion: those five original reproductions pass, but the broader asynchronous identity and concurrent-retry boundaries are not complete. The recommended corrections are to revalidate identity after asynchronous work, preserve tagged intents on receipt ownership conflicts, and receipt-reconcile a mutation 409 before discarding its retry ID. The reviewer also noted a minor legacy-receipt form-error path; it has not been independently reproduced.

## Asynchronous actor and retry completion (2026-10-05)

All three historical findings now have implementation fixes and regression coverage:

- The captured form actor is checked after each receipt await and before/after the write. All eight service mutation routes and receipt GET additionally compare the optional URI-encoded `X-Travel-Service-Actor` with the same request's authenticated identity, using the verifier's Unicode `casefold` normalization. Malformed encoding is 400; actor mismatch is **412**, distinct from business/fingerprint 409. This header only rejects a changed actor; it never grants access or changes the authenticated actor. Legacy API clients may omit it without changing stored payload fingerprints or schema.
- Read-only recovery probes all retained UUIDs through the existing owner-only receipt endpoint. A committed ownership proof clears the intent, including historical incorrectly tagged/quarantined records. Foreign uncommitted UUIDs never become mutation candidates. Tagged ownership conflicts remain stored; only actor-less legacy metadata receives `unavailable_for`. The form's receipt-error path also retains its UUID and offers confirmation instead of replaying blindly.
- Every mutation 4xx except identity 412 is receipt-reconciled **before** discarding a UUID, including create and settlement. Committed responses show the actual original saved order. Confirmed uncommitted responses allow validation/revision correction only after the same-actor check. Unknown, unavailable, auth-expired, foreign and 412 outcomes retain the UUID and frozen body. Visible contact is redacted on expiry; the sent snapshot remains immutable in memory until confirmation or leaving the form and is never persisted to session storage.
